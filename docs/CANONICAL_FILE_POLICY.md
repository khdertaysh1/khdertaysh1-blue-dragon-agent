# Canonical path policy repair

Confirmed on 9f6ef52 by the independent review and our actual CLI baseline: `alias.txt -> .env`, reached after an invalid `path=42` then corrected path, allowed `read_file` and `read_lines` to send a synthetic secret to the next provider request. `local_file_path` already checked canonical protected components, while their older shared `resolve` checked only lexical components and workspace containment.

`tools.rs::resolve` now validates protected components on the canonical target for every caller. For new files/directories it validates the canonical parent and returns a path under that checked parent. A dangling symlink is an existing filesystem entry and cannot be mistaken for a new writable file. Existing in-workspace aliases to permitted files remain readable/writable after the usual approval. Approval itself does not bypass target validation; writes resolve again after approval and compare the target and original contents.

Audited direct consumers: `read_file`, `read_lines`, `file_info`, `list_files`, `read_file_window`, `search_file`, `file_outline`, `search_files`, `write_file`, `edit_file`, `multi_edit_file`, `create_directory`. Project and structural directory scans already skip symlinks; proposed delegate edits independently reject symlinks/hardlinks. This policy is not a sandbox around approved subprocesses or arbitrary Git/browser behavior.

Tests: actual CLI invalid→corrected alias reads for seven tools, permitted alias, protected file, protected directory alias and external-workspace alias (28 cases), inspecting provider packets and saved outputs for the synthetic secret. Old baseline deliberately uses only a fake secret. Rust tests also cover writes/edits and directory creation, dangling external links, absence of approval for rejected targets, approved allowed-alias writes, and an alias changed to `.env` during approval. No real secret or external service is used.

Limit: canonical validation and later open/rename are not an OS-enforced capability boundary. A hostile external filesystem writer can race between checks and I/O; the approval-time replacement is tested and rejected, but general TOCTOU elimination would require directory-handle/openat-style operations across all components/platforms. No actual Termux or Windows/macOS filesystem validation is claimed. POSIX CLI symlink tests explicitly skip unsupported platforms instead of reporting a device pass.
